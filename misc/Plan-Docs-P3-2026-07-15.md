### `docs/data-model.md` — what it will say

The game's units, classes, and rules are not hard-coded — they live in data files (JSON: plain-text
lists of names and numbers) that the client reads at startup. This doc explains, once, the
three-part naming pattern the whole codebase uses to read those files — **Def** (the finished,
typed object the game code asks questions of), **Vars** (the checker/converter that turns raw text
into a Def), **Wrangler** (the fetcher that loads and collects them) — then follows one real
example end to end: how a character class like "Axemaster" travels from a data file to a unit on
your roster.

1. **The three-part pattern, once** — Def / Vars / Wrangler, using character classes as the worked
   example; key framing: it's a naming _convention_ the code follows, not one shared base class —
   only the small loader trio and the validation gate are actually shared.
2. **When the data loads** — most of it in one batch during boot; campaign data only when needed.
3. **Class definitions are templates** — what a character _class_ knows: stat ranges (min/max),
   ability lists, appearances, and how classes inherit from a parent class.
4. **Unit definitions are your actual units** — each roster unit carries its own concrete stats and
   ability levels; the live in-battle object wraps one of these. One clause on the "pretend stats"
   used during AI simulation → link `offline-ai.md`.
5. **Your account and roster** — how the server's account answer becomes the roster, party, and
   renown you see; states plainly the rule that keeps resurfacing in debugging, worded at the time as
   "in battle, units use their roster numbers — class definitions only set the allowed min/max".
   **Overturned 2026-08-21:** measurement showed units fight with the numbers sent with the battle,
   on both players' screens. Kept here as the record of what this tier wrote; the settled answer is
   `docs/data-model.md` §5 and `bsf-server/docs/client-contract.md` → R13.
6. **Naming traps** — the word "Vars" means three different things in this codebase; the folder
   `game/entity/` does NOT hold the entity model; the schema check silently does nothing unless
   it's wired up; and the 2013 source is stale for these files (read the decompile).
7. **Where to read more** — cross-references.

### `docs/offline-ai.md` — what it will say

Our fork added something the original game never shipped: a practice battle against the computer,
fully offline — the game never talks to the server during it. This doc explains how to start one,
how the computer decides its moves, what it's bad at, and the small fixes we made so it doesn't
crash with modern parties.

1. **What it is** — practice battles against the computer (and a planned watch-two-AIs mode); no
   renown or rewards; zero server traffic during the battle.
2. **How to start one** — the hidden keyboard shortcut (Ctrl+Shift+A) or a mod-host command; the
   computer's team is a mirror copy of _your_ party. Also sets the record straight: the
   offline-looking screens Stoic left behind are empty stubs, not a real offline mode — ours is new.
3. **Same battle engine as multiplayer — said precisely** — an offline battle runs the _identical_
   turn state machine and the same seeded dice (so battles are reproducible); the one step it skips
   is the per-turn checksum-and-sync exchange, because there is no second client to compare against.
   Cite `battle-engine.md`, never re-explain it.
4. **How the computer takes a turn** — it waits half a second, then scores every "walk here and hit
   that enemy" option it can find and plays the highest-scoring one; kills earn a big bonus; if
   nothing is reachable it moves closer or rests.
5. **What it can't do, and the "imagined move" trick** — it never uses special abilities (they are
   never even considered) and has no team-up focus-fire; to score a move it _simulates_ the hit on a
   scratch copy that undoes itself, so scoring never touches the real board or the shared dice.
6. **What our fork fixed** — three small guards so units without a standard attack, or scenery
   objects on the board, don't crash the planner; the separate loading hang was fixed elsewhere —
   link the two tracked fix plans.
7. **Known gaps** — the portraits finding, spectator mode planned-but-not-built, Ranked/Tournament
   stay online-only; a short "try it yourself" note. (The AI _improvement_ roadmap is deliberately
   not in this doc.)

### `docs/mod-bridge.md` — what it will say

Our fork lets an outside helper program (a "mod host") watch and steer the game without hacking the
game file again and again: the client launches `mods/host.exe` and the two talk over plain text —
one small JSON message per line. This doc is the contract a mod author needs, plus one loudly-flagged
warning: today the login message (password / Discord token) gets forwarded to the host too, so
nobody should ship builds that run untrusted hosts until the planned fix lands.

1. **What it is and why** — mod the game through one permanent patch + an external program, instead
   of repeated game-file surgery.
2. **The messages** — one JSON object per line, in both directions; the three reply shapes; how big
   or multi-line data is repackaged so it can't break the one-line rule; the host's three duties
   (keep stdout for protocol only, log to stderr, quit when its input closes).
3. **What the game can send** — the six entry points, in a table, plus the spectator on/off flag.
4. **The host's life** — where the host must live; it's only started the first time the game talks
   to the server; restarted at most 3 times if it crashes; politely told to shut down (then
   force-killed) when the game exits; and if anything is missing, the bridge switches itself off and
   the game runs completely normally.
5. **Commands** — how the host asks the game to do things; the two built-ins (`ping`,
   `set_spectator`); `start_ai_battle` added at runtime by the game-flow code; how replies and
   errors are matched up by id.
6. **The HTTP tap** — every request the game sends, and every raw answer it receives, is copied to
   the host; gotcha: a retried request is copied twice, so hosts must de-duplicate.
7. **Who reads the spectator flag** — what consumes it today (link `offline-ai.md`), what is only
   planned.
8. **⚠ Known security gap** — credentials and the session key are currently forwarded word-for-word;
   link the already-public finding (§3.2) and its planned Wave-2 fix; plain advice: only run a host
   you wrote or trust.
